# NixOS configuration (Dendritic pattern)

Personal NixOS configuration built on the Dendritic pattern using flake-parts,
import-tree and flake-file. Andrew is the repository administrator; Claude
proposes changes through pull requests and Andrew reviews, tests and merges
them.

## This repository is public

- Never commit secrets: passwords or password hashes, API tokens, Wi-Fi keys,
  VPN keys, private SSH/GPG keys, or anything similar.
- Anything sensitive goes through the secrets feature module (sops-nix or
  agenix, to be added). If a feature needs a secret and that module doesn't
  exist yet, stop and say so rather than working around it.
- Secrets used by command-line tools are injected by wrapping the tool with
  `wrapWithSecrets` (`modules/flake/lib.nix`). Never export them in a shell
  init. See `docs/secrets.md`.

## flake.nix is generated

- `flake.nix` is generated by flake-file from the modules. **Never edit it by
  hand.** Any manual change will be overwritten and will fail `nix flake check`.
- Flake inputs are declared in the module that uses them, with
  `flake-file.inputs.<name>`, next to the configuration that needs them.
  Example:

  ```nix
  # modules/features/example.nix
  { inputs, ... }:
  {
    flake-file.inputs.example = {
      url = "github:owner/example";
      inputs.nixpkgs.follows = "nixpkgs";
    };

    flake.modules.nixos.example = {
      imports = [ inputs.example.nixosModules.default ];
    };
  }
  ```

- Inputs shared by many features (nixpkgs, home-manager) are declared once in
  a module under `modules/flake/`, not repeated in each feature.
- Add `inputs.nixpkgs.follows = "nixpkgs"` to every input that accepts it,
  unless there's a specific reason not to (state the reason in the PR).
- After adding, removing or changing any `flake-file.*` option:
  1. Regenerate with `nix run .#write-flake`
  2. Update the lock with `nix flake lock`
  3. Commit `flake.nix` and `flake.lock` in the same commit as the module
     change.
- Only update existing input revisions (`nix flake update`) in a dedicated
  `chore/update-inputs` PR, never as a side effect of a feature PR.

## Architecture rules

- Every `.nix` file under `modules/` is a flake-parts module. Never place a
  plain NixOS or home-manager module there directly.
- The flake-file `dendritic` flake module provides the flake-parts and
  import-tree wiring; don't reimplement it.
- One feature (aspect) per file. A feature publishes its parts from that one
  file into `flake.modules.nixos.<name>` and/or
  `flake.modules.homeManager.<name>`, and declares any inputs it needs.
- Hosts live under `modules/hosts/<host>/` and compose features by name via
  `config.flake.modules.*`. Hosts never import feature files by path.
- import-tree ignores any path containing `/_`. Use this for
  `hardware-configuration.nix` and other non-flake-parts files, and import
  them explicitly from the host.
- Prefer existing nixpkgs and home-manager options. Only define custom
  options when a feature genuinely needs to be configurable.
- Once a formatter is configured, run `nix fmt` before every commit.

## Workflow

- Never commit or push to `main`. Use one branch per change:
  `feat/<name>`, `fix/<name>` or `chore/<name>`.
- Use conventional commit messages (`feat:`, `fix:`, `chore:`, `docs:`).
- Before opening a PR, run `nix run .#write-flake` (it should produce no
  diff), then `nix flake check`, then build every affected host:
  `nix build .#nixosConfigurations.<host>.config.system.build.toplevel`
- Never run `nixos-rebuild` (switch, test or boot) and never use `sudo`.
  Andrew applies changes to real machines.
- Open PRs with `gh pr create`, filling in the PR template. List any new or
  changed flake inputs in the PR description. Never merge.
- Keep each PR to a single feature. If you notice something unrelated,
  note it in the PR description instead of fixing it.
- If a design choice is unclear, ask before implementing.

## Hosts

| Host | Hardware | Role |
|---|---|---|
| `surface-laptop` | Microsoft Surface Pro | Productivity machine. Not used for gaming. |
| `tiki-rig` | Desktop PC | Everything `surface-laptop` has, plus gaming. |

### How hosts share features

- Hosts never import another host. Shared functionality lives in feature
  aspects, which each host imports by name.
- Group the common feature set into a shared aspect (e.g. `workstation`)
  that both hosts import. `tiki-rig` additionally imports a `gaming` aspect.
- Anything hardware-specific stays in that host's own directory: kernel,
  firmware, drivers, power management, display scaling, input devices and
  `hardware-configuration.nix`.

### Host notes

- **surface-laptop**: Surface hardware support (touchscreen, pen, cameras,
  battery and power management) is hardware-specific and belongs to this
  host only. Check nixos-hardware for a matching Surface module before
  writing anything custom. Battery life and suspend matter on this machine.
- **tiki-rig**: Gaming support (Steam, Proton, GPU drivers and related
  tooling) belongs in the `gaming` aspect or the host's hardware config,
  never in `workstation`, so it can't leak onto `surface-laptop`. Confirm
  the GPU vendor with Andrew before adding graphics drivers.
